> [!CAUTION]
> Скрипт делает бэкап и восстанавливает **директорию и базу данных Remnawave**, а также (по желанию) **Telegram-магазин**. Бэкап и восстановление других сервисов и настроек остаются на вашей стороне. Внимательно читайте подсказки скрипта, прежде чем подтверждать действия.

> [!IMPORTANT]
> **С версии 4.3.0 Google Drive не поддерживается.** Если бэкапы отправлялись в Google Drive, скрипт сам переключится на Telegram и сообщит об этом. Для бэкапов больше 50 МБ подключите S3.

## 🚀 Установка

Нужны права root.

```bash
curl -o ~/backup-restore.sh https://raw.githubusercontent.com/distillium/remnawave-backup-restore/main/backup-restore.sh && chmod +x ~/backup-restore.sh && ~/backup-restore.sh
```

При первом запуске скрипт спросит язык, режим работы и данные Telegram, а затем установится в `/opt/rw-backup-restore`. Дальше меню открывается командой `rw-backup` из любой папки.

## ✨ Возможности

**Бэкап**
- вручную из меню или автоматически по расписанию
- три режима: панель и бот, только панель, только бот
- поддержка Docker-базы панели и внешней PostgreSQL
- имя архива показывает, что внутри: `full`, `panel` или `bot`
- шифрование бэкапов ключом [age](https://github.com/FiloSottile/age), по желанию

**Отправка и хранение**
- в Telegram (в личку боту или в топик группы) или в S3-совместимые хранилища, до 5 одновременно
- проверка размера перед отправкой в Telegram (лимит 50 МБ) с уведомлением, если бэкап не влез
- отдельные сроки хранения на сервере (в днях или часах) и в каждом S3
- занятое место на диске и в S3 в главном меню и в уведомлениях, с лимитом для S3 по желанию

**Восстановление**
- выборочно: всё, только база или только файлы, отдельно для панели и для бота
- метаданные бэкапа перед восстановлением: версия скрипта, панели, тип дампа
- имя и пользователь базы данных определяются автоматически из контейнера

**Удобство**
- меню со стрелками, выбором по номеру и Esc для возврата
- карточка состояния: что бэкапится, последний бэкап, расписание, шифрование, место на дисках
- проверка подключения к S3 и прокси Telegram с понятной диагностикой ошибок
- тестовое сообщение в Telegram из настроек
- уведомления о новой версии и автообновление по желанию
- при удалении скрипта локальные бэкапы можно сохранить

## 🔄 О выборочном восстановлении

Если в бэкапе есть и база данных, и файлы (панели или бота), скрипт спросит, что восстановить:

| Вариант | Что происходит |
|---|---|
| **Всё** | восстанавливаются и база, и файлы |
| **Только база данных** | том БД пересоздаётся с нуля, файлы панели или бота не трогаются. Нужна папка с уже установленной панелью или ботом |
| **Только файлы** | заменяются файлы и настройки, база данных не трогается |

Например, так можно откатить только базу после неудачного обновления и не трогать текущие настройки.

## 🔐 Шифрование

Бэкапы шифруются публичным ключом [age](https://github.com/FiloSottile/age) и сохраняются как `.tar.gz.age`. На сервере хранится только публичный ключ, поэтому даже с доступом к серверу или хранилищу бэкап не прочитать. Для восстановления скрипт попросит приватный ключ.

> [!WARNING]
> Сохраните приватный ключ в надёжном месте. Без него зашифрованный бэкап восстановить невозможно.

Включается в **Настройки → Шифрование**: можно создать новую пару ключей или использовать свою.

## 📦 Переезд на другой сервер

<details>
  <summary>📝 Только панель: переход на новый сервер</summary>
  <br>

1. В Cloudflare направьте поддомен панели на новый IP. Если на новый сервер переезжают и другие сервисы, обновите и их поддомены.
2. Восстановите директорию и БД.
3. Если нужно, восстановите сертификаты для домена.
4. Ссылка доступа и пароль останутся от старой панели, с которой делался бэкап.
5. На всех нодах замените правило для сервисного порта (по умолчанию 2222), чтобы панель с новым IP могла с ними связаться. Выполните на каждой ноде, подставив свои `OLD_IP` и `NEW_IP`:

```bash
ufw delete allow from OLD_IP to any port 2222 && ufw allow from NEW_IP to any port 2222
```

Готово. Осталось поставить и настроить остальные нужные сервисы (например, kuma, beszel).

</details>

<details>
  <summary>📝 Панель + нода: переход на новый сервер</summary>
  <br>

1. В Cloudflare направьте на новый IP поддомены панели и «корневой» ноды (которая стоит вместе с панелью). Если на новый сервер переезжают и другие сервисы, обновите и их поддомены.
2. Если нужно, восстановите сертификаты для домена.
3. Восстановите директорию и БД.
4. Откройте доступ к панели через порт 8443 (скрипт от eGames, пункт «Управление доступом к панели»).
5. Ссылка доступа и пароль останутся от старой панели, с которой делался бэкап.
6. В управлении нодами найдите корневую ноду. В ней указан адрес старого сервера: замените его на новый, и нода включится сама.
7. Закройте доступ к панели через порт 8443 так же, как открывали.
8. На всех внешних нодах замените правило для сервисного порта (по умолчанию 2222). Выполните на каждой ноде, подставив свои `OLD_IP` и `NEW_IP`:

```bash
ufw delete allow from OLD_IP to any port 2222 && ufw allow from NEW_IP to any port 2222
```

Готово. Осталось поставить и настроить остальные нужные сервисы (например, kuma, beszel).

</details>

## ⌨️ Команды

| Команда | Что делает |
|---|---|
| `rw-backup` | открыть меню |
| `rw-backup backup` | создать бэкап без меню (так работает расписание) |
| `rw-backup restore` | восстановить из бэкапа |
| `rw-backup update` | обновить скрипт |
| `rw-backup remove` | удалить скрипт |
